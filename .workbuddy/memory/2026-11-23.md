## P3 第二批：incremental 快速判活（--fast-cache）

- **先推翻一个错误前提**：Query 编译产物磁盘缓存不可行也无收益。实测空目录 + 50 规则 = 71ms（vs `--help` 66ms），50 条 Query 编译仅 ~5–20ms；tree-sitter/绑定无 Query 序列化 API。真瓶颈是 grammar 表构造 **~233ms/语言**（`@language.Language::from_compact_base64` 解 LZ + 重建 LEB128 表，已是序列化格式，无更快路径）。6 语言 1.33s，与文件数无关（半量分片仍 1.5s）。复现：`python3 scripts/bench_coldstart.py`。
- **实现**：`--fast-cache`（隐含 `--incremental`）。旁路 probe：`<cache_dir>/probe/<sha256(path|size|mtime)>` → `{path,size,mtime_sec,mtime_nsec,content_hash,entry_key}`。快路径只 stat，不读内容；probe 命中即用记录的 entry_key+content_hash 加载条目，任何失败回退严格路径。probe 仅在开关开启时写入，默认缓存布局不变。
- **收益**：缓存全热重复扫描，158KB 小文件 192→198ms（0.97×，无收益）；12MB（120×100KB）381→139ms，**2.74×**。适用大文件仓库。
- **风险（已用 cram 钉住）**：同 size + 同 mtime 改内容 → fast 陈旧命中（findings 1），严格路径检出（findings 0）；touch 后 fast 立即失效。默认关闭。
- 验收：单测 146/146、cram 20/20、golden 100%/0%、verify 10 步全绿（覆盖率 90.9%）。

### 实测坑（P3 第二批）
- **`@fs.mtime` 返回 `Timestamp` = `(Int64, Int)` 元组**，不是带 `sec()/nsec()` 方法的类型；用 `let (sec, nsec) = @fs.mtime(p)` 解构。nsec 是 `Int`，字段别声明成 `Int32`（Int 无 `to_int32()`）。
- **cram 每个 ```mooncram 块只接受一条 `$` 命令**：后续 `$` 行会被当成期望输出的一部分（全标 `-`）。多步演示必须用 `&&` / `;` 串成一行。块内空行也会断块。
- `scan.exe` 在 cram 里由工具注入 PATH；`--format json` 时不打印 `cache: N hit` 行（只有 console + incremental 才打印），验证命中要用 console。

## P3 第三批：fast-cache 冷热精确对比（--copies 6）

- `bench_scan.py` 扩展 `--cache-mode none|strict|fast|both`：cold 每次清缓存、warm 先预热一次；用 `--format console,json` 同时拿 `cache: H hit, M miss` 与 findings 数。
- **--copies 6（900 × ~1KB，950KB）实测**（runs=3，两次复跑一致）：严格 冷 5.22s / 热 2.00s；fast 冷 7.24s / 热 2.00s。即 **热跑 1.00×（小文件无收益）**、**冷跑慢 38%**（每文件多写一个 probe，Windows 上 ~2.4ms/个）。
- **14MB 级冷跑的真问题**：120 × 100KB JS 单次扫描 **5 分 38 秒**（含 0.4s 解析 + 50 规则 × ~45ms/规则）。规则数敏感性：1 条 0.66s、5 条 1.54s、50 条 2.77s → 冷路径 85% 在规则匹配，不是 IO，fast-cache 帮不上。
- 结论：fast-cache 只优化热路径且只对**大文件**有效（12MB 热跑 381ms→139ms，2.74×）；首轮大文件慢属另一问题（规则裁剪/分片，P4）。

### 实测坑（P3 第三批）
- **`--copies N` 只是复制小文件**，不代表真实规模：950KB/900 文件的结论与 12MB/120 文件相反，评估性能必须按"文件大小分布"报告，不能只报文件数。
- Windows 上创建小文件约 2.4ms/个，凡"每文件写一个文件"的设计（probe、cache entry）在小文件海量场景会成为主要成本。

- 结论：fast-cache 只优化热路径且只对**大文件**有效（12MB 热跑 381ms→139ms，2.74×）；首轮大文件慢属另一问题（规则裁剪/分片，P4）。

### 实测坑（P3 第三批）
- **`--copies N` 只是复制小文件**，不代表真实规模：950KB/900 文件的结论与 12MB/120 文件相反，评估性能必须按"文件大小分布"报告，不能只报文件数。
- Windows 上创建小文件约 2.4ms/个，凡"每文件写一个文件"的设计（probe、cache entry）在小文件海量场景会成为主要成本。
